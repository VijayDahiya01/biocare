ZepIris Integration

1. ZepIris integration
ZepIris is the open-source face authentication engine at the core. It runs as two services (a main API and an ML inference service) and the platform's own face-auth service calls it. This section explains how to deploy and call it.

1.2 Service ports
ZepIris Main API        :8000   ← platform calls this
ZepIris ML Inference    :8001   ← internal, called by 8000
Milvus                  :19530
MinIO                   :9000
 
The platform's face-auth service calls ZepIris :8000 over the internal network.

1.3 Enroll & search calls
The platform wraps these ZepIris calls inside its own /faces/enroll and /faces/search endpoints (see API Reference). The raw ZepIris calls are:
Enroll:
POST :8000/v1/faces/insert
{ "collection": "faces_<tenant>", "id": "<face_id>", "image": "<base64>" }
 
Search:
POST :8000/v1/faces/search
{ "collection": "faces_<tenant>", "image": "<base64>", "top_k": 5 }
Returns: [{ id, score }, ...] sorted by score desc

Threshold tuning
Default match threshold is 0.5. Above it = match.
For attendance, 0.5 is a good balance. For high-security zones, raise to 0.65–0.7.
Lower thresholds = more false accepts; higher = more false rejects. Make it per-zone configurable.
Always run blur + spoof checks BEFORE accepting a match.

1.4 Per-tenant collections
Each tenant gets its own Milvus collections (faces_<tenant> and blacklist_<tenant>). This guarantees a search never crosses tenant boundaries — the isolation rule extends into the vector database.

Part 3
Security & DevOps

3. Security & DevOps
3.1 Security requirements (mandatory)
Transport: TLS 1.3 on all traffic. No plain HTTP, ever.
At rest: AES-256 encryption for the database and MinIO. Milvus vectors encrypted at rest.
Sessions: HttpOnly, Secure, SameSite=Strict cookies. CSRF tokens on all mutations.
Passwords: Argon2 or bcrypt hashing. TOTP 2FA mandatory for admin roles.
Tenant isolation: PostgreSQL Row-Level Security as a safety net beyond app-layer checks.
Secrets: in a secrets manager or env, never in code or git.
Rate limiting: at the gateway, per the API Reference limits.

3.2 Monitoring
Tool
Watches
Prometheus
Metrics — request rate, latency, error rate, uptime
Grafana
Dashboards and alerting thresholds
Audit logs
Every significant action (in PostgreSQL)
Health checks
Each container exposes /health; gateway probes it

3.3 Backups
PostgreSQL: daily automated dump, retained 30 days; point-in-time recovery enabled.
Milvus & MinIO: daily snapshot.
Restore drills: test a full restore monthly. A backup you haven't restored is not a backup.

3.4 CI/CD
Pipeline: on push → lint → test → build images → deploy to staging → manual approval → production.
Migrations: database migrations run automatically and must be reversible.
Zero-downtime: rolling deploys; the face-search path must never be fully down.
