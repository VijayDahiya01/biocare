Part 3
Main API — Verified Endpoints

3. Main API (port 8000)
All face operations the platform calls. These are the real signatures from the repository.
3.1 Insert a face
POST
/v1/faces/insert

Multipart form. Registers a new face. Returns 409 if the id already exists, 422 if image-quality assessment fails or no face is detected.
curl -X POST http://localhost:8000/v1/faces/insert \
  -F "id=employee_001" \
  -F "tenant=acme_corp" \
  -F "file=@face.jpg"
 
Response 200:
{
  "requestId": "a1b2c3d4-...",
  "imageQualityAssessment": {
    "passed": true,
    "nudity": { "is_safe": true,  "probability": 0.02 },
    "spoof":  { "is_spoof": false, "probability": 0.05 },
    "blur":   { "is_sharp": true,  "probability": 0.10 }
  },
  "userOperationResult": { "operation": "INSERT", "status": "success" }
}

3.2 Search for a face (check-in)
POST
/v1/faces/search

Multipart form. top_k and threshold are query parameters. Returns 200 with an empty matches array if IQA fails or no face is found — it does NOT error on a bad image. The platform's own /faces/search endpoint wraps this and then applies toggle logic to record attendance.
curl -X POST "http://localhost:8000/v1/faces/search?top_k=5" \
  -F "id=query_001" \
  -F "tenant=acme_corp" \
  -F "file=@query_face.jpg"
 
Response 200:
{
  "requestId": "d4e5f6a7-...",
  "imageQualityAssessment": { "passed": true, ... },
  "searchResult": { "matches": [ { "id": "employee_001", "score": 0.92 } ] }
}
 
Query params: top_k (default 5), threshold (default ZEPIRIS_MILVUS_SEARCH_THRESHOLD=0.5)

3.3 Upsert a face
POST
/v1/faces/upsert

Multipart form. Insert or update. Same response shape as insert, with operation = UPSERT. Use this for re-enrollment (a person updating their face).

3.4 Delete a face
DELETE
/v1/faces/delete

Query parameter id. Part of the platform's erasure cascade — this removes the vector from Milvus.
curl -X DELETE "http://localhost:8000/v1/faces/delete?id=employee_001"
 
Response 200:
{ "requestId": "...", "userOperationResult": { "operation": "DELETE", "status": "success" } }

3.5 Get face metadata
GET
/v1/faces/get/{face_id}

curl http://localhost:8000/v1/faces/get/employee_001
 
Response 200:
{ "face_id": "employee_001", "tenant": "acme_corp", "object_key": "faces/employee_001" }

3.6 Health & readiness
GET
/healthz

GET
/readyz

Both return {"status": "ok"}. Use /readyz for orchestration readiness probes, /healthz for liveness.

4. ML Inference (port 8001)
Internal service. The Main API calls these; the platform normally does not call them directly. Unlike the Main API, these take base64 JSON, not file uploads. Documented here so the freelancer understands the full pipeline and can tune thresholds.
4.1 Common payload
All ML POST endpoints take:
{ "image_b64": "<base64-encoded image bytes>" }

Each ML model loads from a .pth file on startup (default /app/models/{nudity,spoof,blur}_model.pth).

Models can take 30–60 seconds to load on first start — build readiness probes accordingly.

5. Milvus schema (verified)
ZepIris uses ONE Milvus collection. This is different from the platform's other per-tenant stores — here, tenant is a column.
Collection: zepiris_faces
  face_id      VARCHAR(128)       primary key
  tenant       VARCHAR(256)       multi-tenancy
  object_key   VARCHAR(512)       MinIO image path
  embedding    FLOAT_VECTOR(512)  face vector
 
Index: FLAT, metric COSINE

7. How the platform wraps ZepIris
To keep the platform's own clean API (documented in Document 2) while using the real ZepIris underneath, build a thin adapter in the face-auth service:
Platform receives a base64 image from the browser (its own API stays base64-friendly for the web).
The adapter decodes the base64 to bytes and posts them as a multipart file to ZepIris, adding the tenant form field from the session.
It maps ZepIris's response (requestId, imageQualityAssessment, searchResult.matches) into the platform's own envelope (success, data, request_id).
On search, it reads matches[0] and applies toggle logic to record the attendance event.
On erasure, it calls DELETE /v1/faces/delete plus removes the MinIO object and Postgres records.

This adapter is the single most important integration component
Isolating ZepIris behind one adapter means: if ZepIris changes, only the adapter changes.
It also lets the platform present a consistent, web-friendly, base64 API to the frontend while ZepIris uses multipart underneath.
Specify and test this adapter first — everything else depends on it.
