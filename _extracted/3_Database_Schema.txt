1.1 Conventions
Primary keys are UUIDs (type uuid, default gen_random_uuid()).
Every tenant-owned table has a tenant_id column with a foreign key to tenants and an index. This enforces isolation.
Timestamps are timestamptz (with timezone), default now().
Soft deletes use a deleted_at column where history must be kept; hard deletes are used for biometric erasure.
Enums are implemented as Postgres enum types or text with a CHECK constraint.

The golden isolation rule
EVERY query against a tenant-owned table MUST include WHERE tenant_id = <session tenant>.
Enforce this with PostgreSQL Row-Level Security (RLS) policies as a safety net — do not rely on application code alone.
A single missed filter is a cross-tenant data leak and a DPDP breach.

Part 5
Milvus, MinIO & Redis

5. Non-relational stores
5.1 Milvus (vector database)
Stores the 512-dimension face vectors. Two collections per tenant keep enrolled faces and blacklist faces separate but both searchable.
Collection: faces_<tenant_id>
  Fields:
    vector_id   VARCHAR  (primary key, matches face_records)
    embedding   FLOAT_VECTOR[512]
    user_id     VARCHAR
  Index: IVF_FLAT or HNSW, metric_type = COSINE
 
Collection: blacklist_<tenant_id>   (same schema)
 
Search: top_k = 5, COSINE similarity, threshold default 0.5

5.2 MinIO (object storage)
S3-compatible storage for images and generated files. Raw face images are deleted immediately after the vector is generated; only documents and receipts persist.
Bucket layout (per tenant prefix):
  <tenant>/faces/<face_id>.jpg        ← deleted after embedding
  <tenant>/documents/<id>.pdf         ← consent forms, scans
  <tenant>/receipts/<id>.pdf          ← donation 80G receipts
  <tenant>/certificates/<ref>.pdf     ← erasure certificates
 
Server-side encryption: enabled (SSE-S3)

5.3 Redis (cache & sessions)
In-memory store for sessions, rate limiting, and hot lookups. All keys have a TTL.
session:<session_id>      → user_id, tenant_id, role   (TTL 8h admin / 4h member)
csrf:<session_id>         → csrf token                 (TTL = session)
ratelimit:<key>           → counter                    (TTL 60s)
otp:<email>               → code                       (TTL 10min)
presence:<tenant>         → cached inside-count         (TTL 30s)

Erasure touches all four stores
When a user is erased: delete their Milvus vector, their MinIO images, their Postgres face_records + personal data, and flush their Redis sessions.
Each deletion is verified independently before the erasure is marked complete.
See the DPDP & Security document for the full cascade.
